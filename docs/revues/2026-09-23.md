## Détail des constats hauts et moyens

### 1. La dérivation de toutes les graines repose sur un caractère NUL brut, invisible, que Git traite comme binaire

`graineDepuisTexte` (`validation/domaine/alea.ts:30`) joint ses composants par un octet `0x00` écrit
tel quel dans le source, pas par l'échappement `\0`. Même chose pour deux clés de regroupement
(`metriques.ts:172`, `tendance.ts:34`). Trois conséquences :
- à l'écran, le séparateur ressemble à une espace ; le relecteur de cette revue l'a lu ainsi. Un
  éditeur qui le remplace, ou un contributeur qui le « corrige », change **toutes** les graines
  (tirage, bootstrap, permutation, ordre des lots) sans qu'aucun test ne rougisse : aucun ne fige la
  sortie de `graineDepuisTexte` ;
- Git classe ces fichiers comme binaires : une PR qui les modifie affiche « Binary files differ »,
  donc un changement du code de mesure échappe à la relecture ;
- un tiers qui réimplémente `splitmix64-sha256-v1` pour rejouer un tirage (§9) ne peut pas lire le
  séparateur dans le source.

**Correction**, sans changement de comportement : écrire `"\0"` (la chaîne est identique octet pour
octet), figer la sortie de `graineDepuisTexte` sur trois entrées par un test, écrire le séparateur
dans la docstring de l'algorithme, et ajouter à `pnpm test` un test bloquant « aucun caractère de
contrôle hors tabulation et saut de ligne dans un fichier source suivi ».

### 2. Aucune donnée n'est validée contre son schéma à l'exécution, ni en entrée ni en sortie vers `data/`

CLAUDE.md exige une validation de schéma à chaque frontière. Aujourd'hui, ajv ne valide que les
exemples de `schema/`. Les items et mesures de `staging/`, le journal, les brouillons, le corps des
requêtes HTTP, les entrées de `pnpm symmetry` sont lus par `JSON.parse(...) as T` ; l'item que
`pnpm promote` écrit dans `data/` (corrections appliquées) n'est confronté à rien. Deux scénarios
concrets :
- une requête `POST /api/decisions` portant `decision: "approuver"` est acceptée
  (`construireDecision` ne vérifie pas l'énumération), écrite au journal, puis comptée
  « non évaluable » dans le kappa publié par `categorieDe` ;
- une correction qui écrit une `position` hors vocabulaire produit un item promu non conforme à
  `item.schema.json`, que le §9 publie.

Points déjà connus : `docs/DETTE.md`, 2026-09-20, points 1 (journal) et 2 (`ecrireLot`).

**Correction proposée** : une seule fonction `valider(nom, valeur)` sur le registre ajv existant
(`outils/schemas/registre.ts`), appelée à chaque lecture et écriture listée ci-dessus. **Décision de
l'auteur** : cela met ajv dans le chemin d'exécution de l'interface de validation et de la
promotion (ajv passe de `devDependencies` à `dependencies`), ce que la dette du 2026-09-20 laissait
« à trancher ».

### 3. `pnpm promote --ecrire` réécrit tout item déjà promu dans `data/`

`ecrire()` fait `writeFileSync(data/items/<id>.json)` pour chaque issue « promouvoir », sans regarder
si le fichier existe. Tant que l'item reste dans `staging/` avec ses deux décisions, chaque
`--ecrire` le réécrit depuis son état de staging : un nouvel horodatage et un nouveau commit dans
l'historique au mieux, et au pire la perte de ce qui a été écrit dans `data/` depuis (contestation,
décision du panel). Le diff Git le montre, mais noyé dans un commit « promotion de N items ».

**Correction** : refuser d'écraser un item présent dans `data/` (le signaler dans le rapport, code de
sortie non nul), comme le fait déjà la collecte pour ses manifestes.

### 4. Un item d'un lot absent de `staging/` est sauté sans trace par la promotion

`evaluerLot` fait `if (item === undefined) continue;`. Un item jugé par deux annotateurs mais
disparu de `staging/` (renommé, supprimé, identifiant mal recopié) n'est ni promu, ni en attente,
ni en arbitrage : il n'apparaît nulle part dans le rapport, et la couverture du candidat baisse.

**Correction** : une section « items du lot introuvables dans staging » dans le rapport, et un code
de sortie non nul.

### 5. Les énumérations du protocole sont recopiées en TypeScript sans test d'accord

`Theme`, `Gabarit`, `Registre`, `TypeItem` et d'autres sont déclarés dans quatre fichiers de types.
`validation/io/referentiels.ts` lit bien les thèmes dans `commun.schema.json`, mais les autres copies
ne sont confrontées à rien. Un thème ou un gabarit ajouté au schéma par amendement passerait
inaperçu : `THEMES` de `pipeline/questions/types.ts` borne les strates du tirage.

**Correction** : un test d'égalité entre chaque liste TypeScript et l'énumération du schéma (le
test, pas une génération de code).

### 6. La règle « item tirable » est écrite deux fois

`itemEngendreDesQuestions` (`engendrement.ts`) et le corps de `questionTirable` (`tirage.ts`)
écrivent chacun `statut_validation === "verifie" && contestationPermetLeTirage(item)`.

**Correction** : `questionTirable` appelle `itemEngendreDesQuestions`.

### 7. Le gabarit d'attribution est reconnu par son code

`engendrement.ts:192` (`gabarit.code !== "Q-ATT"`) et `symetrie.ts:310` décident sur le code, alors
que la docstring du module affirme « ce module ne teste jamais un code de gabarit » et que la table
porte déjà la donnée `nomme_candidat`.

**Correction** : décider sur `!gabarit.nomme_candidat` (comportement identique avec la table
actuelle). Si l'auteur veut distinguer « ne nomme pas » et « attend une liste », c'est un champ de
plus dans `gabarits.schema.json` : décision.

### 8. Un instant sans décalage est lu dans le fuseau de la machine

`instantDe` utilise `Date.parse`, qui lit `2026-12-01T10:00:00` (sans décalage) en heure **locale**.
Le schéma interdit cette forme, mais faute de validation à l'exécution (constat 2), un fichier écrit
à la main passerait, et la réponse attendue d'un item O à la frontière du gel dépendrait du fuseau
de la machine qui calcule le tirage.

**Correction** : refuser tout instant qui ne porte pas de décalage, avec le motif du schéma
`commun#/$defs/instant`.

### 9. La barrière bloquante saute un invariant, et attend un fichier que rien ne produit

`pnpm symmetry` n'examine « item F ⇒ mesure fictive » que si `--mesures` est fourni ; sinon
l'invariant est « annoncé non contrôlé » et la commande peut sortir à 0. La règle 4 de CLAUDE.md
interdit qu'un test de symétrie se saute. Par ailleurs, sa documentation montre
`--items=data/items.json`, alors que `data/` range un fichier par item : aucun outil ne produit ce
tableau.

**Décision de l'auteur** : rendre `--mesures` obligatoire, ou juger que cet invariant n'est pas un
test de symétrie. Dans les deux cas, lire `data/items/` directement.

### 10. Un test d'aveuglement échoue sous Windows

`expect(journal.chemin("lot-001")).toContain("/a1/")` : le chemin porte `\a1\` sous Windows. La CI
Linux est verte, un contributeur sous Windows voit un test rouge qui n'a rien à voir avec son travail.

**Correction** : comparer avec `join("a1", "lot-001.jsonl")` ou `sep`.

### 11. Le client tient en un fichier de 933 lignes

`validation/client/app.ts` mêle état global mutable, rendu de onze écrans, appels réseau, clavier et
chronométrage. Chaque section est lisible ; c'est leur coexistence qui coûte : toute modification
d'un écran oblige à vérifier l'état partagé des dix autres.

**Correction** : un module par section déjà marquée dans le fichier (accueil, lot, item, questions,
soumission, fin de lot, clavier, durées), l'état passé explicitement. Refactoring sans changement de
comportement, en une PR à part.

### 12. Une panne s'affiche comme autre chose, ou pas du tout

`annulerDerniere` attrape toute erreur (`catch {`) et affiche « Aucune décision à annuler dans ce
lot » : une coupure réseau ou une erreur 500 se lit comme un état normal. Les appels lancés par
`void rendreAccueil()` ou `void soumettre()` n'affichent rien en cas d'échec, hors console.

**Correction** : distinguer le 409 attendu (`EchecApi`) des autres erreurs, et un gestionnaire unique
qui affiche l'échec des actions lancées sans `await`.

### 13. Six affirmations de la documentation sont fausses ou périmées

- `analysis/types.ts` : « le dépôt n'a pas encore de validateur JSON Schema côté TypeScript » (ajv y
  est depuis le 2026-09-18) ;
- `pipeline/questions/engendrement.ts` : « ne teste jamais un code de gabarit » (constat 7) ;
- `docs/DETTE.md` : deux entrées réglées non rayées (2026-09-17, « Aucun outil ne mesure la
  complexité » ; 2026-09-17, « Les exemples ne sont pas encore exécutés en intégration continue ») ;
  l'entrée ajv `strict: "log"` compte 135 avertissements, il y en a 185 ;
- `outils/symmetry.ts` : `--items=data/items.json` (constat 9) ;
- `CLAUDE.md` : `pnpm run:dry`, `run:live`, `analyze`, `build:site` n'existent pas (anomalie déjà
  listée dans la feuille de route) ;
- `README.md` : encodé en UTF-16 avec CRLF, donc binaire pour Git et illisible pour la plupart des
  outils (anomalie déjà listée).
